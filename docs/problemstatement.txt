Product Overview
Build a web application called RFP Match for a fictional HR Tech SaaS company called PeopleOS. This is a semantic search tool that helps Sales Engineers find pre-written answers to incoming RFP (Request for Proposal) questions from a curated knowledge base.
The tool takes a question typed by the user, searches a knowledge base of 30 pre-written Q&A pairs using semantic similarity, and returns the top 3 matches with a confidence score and a decision label telling the user what to do with the result.
The application has a Python FastAPI backend and a clean HTML/CSS/JavaScript frontend. It is hosted on Firebase.

Tech Stack

Backend: Python, FastAPI, Google Generative AI SDK (for Gemini text-embedding-004 model), numpy, uvicorn, python-dotenv
Frontend: HTML, CSS, vanilla JavaScript (no frameworks)
Hosting: Firebase Hosting for frontend, backend runs separately
Embedding model: Google Gemini text-embedding-004 via Google AI Studio API (free tier)
No database required — knowledge base is a static JSON file loaded into memory

Backend Specification
embedder.py
This file handles all embedding and similarity logic.
On startup it loads the knowledge base JSON file. It embeds every answer in the knowledge base using the Gemini text-embedding-004 model and stores those embeddings in memory as a list of numpy arrays. This embedding happens once at startup, not on every request.
When a query comes in, it embeds the query using the same model and computes cosine similarity between the query embedding and every knowledge base embedding. It returns the top 3 results sorted by similarity score descending.
Each result includes: the full knowledge base entry, the similarity score as a float between 0 and 1, a confidence tier label, a decision label, a staleness flag, and a decision color.
Confidence tier logic — this is critical and must be exact:

Similarity score 0.85 and above: confidence tier is "High", decision label is "Auto-Answer", decision color is green
Similarity score 0.60 to 0.84: confidence tier is "Medium", decision label is "Review Required", decision color is amber
Similarity score below 0.60: confidence tier is "Low", decision label is "Escalate to SME", decision color is red

Staleness flag logic:
Compare the review_due date in each knowledge base entry against today's date. If review_due is in the past, set is_stale to true. This flag is returned independently of the confidence score — a high confidence match can still be stale.
main.py
FastAPI application with the following:

CORS enabled for all origins (this is a demo application)
Single POST endpoint at /match
Request body: {"question": "string"}
On startup: initialize the embedder, load and embed the knowledge base
The /match endpoint calls the embedder, returns the top 3 results
Also expose a GET endpoint at /health that returns {"status": "ok"}

Response format for /match:
json{
  "query": "the original question text",
  "results": [
    {
      "rank": 1,
      "id": "KB001",
      "category": "Security & Compliance",
      "matched_question": "Does PeopleOS hold SOC 2 Type II certification?",
      "answer": "full answer text",
      "last_updated": "2024-02-15",
      "review_due": "2024-08-15",
      "owner": "Security Team",
      "similarity_score": 0.91,
      "confidence_tier": "High",
      "decision_label": "Auto-Answer",
      "decision_color": "green",
      "is_stale": false
    }
  ]
}

Frontend Specification
Visual Design
Clean, professional, minimal. Dark navy header bar with the PeopleOS logo text in white and a subtitle that says "RFP Response Assistant." White background for the main content area. Use a sans-serif font throughout. The overall feel should be like an internal enterprise tool — functional and trustworthy, not flashy.
Layout
Two-panel layout on desktop. On mobile, panels stack vertically.
Left panel — Query Input (35% width)

Panel title: "Enter RFP Question"
A large textarea for the user to type or paste an RFP question. Placeholder text: "Paste an RFP question here — e.g. Does your platform support Single Sign-On?"
A submit button labeled "Find Matches" in navy blue
Below the button, a small text that says "Searching PeopleOS knowledge base · 30 entries across 6 categories"
When a search is in progress, the button shows a spinner and is disabled
Below the search area, show 6 category chips as visual reference: Security & Compliance, Integrations & APIs, Implementation & Onboarding, Pricing & Licensing, SLAs & Support, Customer References. These are display only, not clickable filters.

Right panel — Results (65% width)
Default state before any search: show a centered empty state message — "Results will appear here. Enter a question on the left to search the knowledge base."
After a search, show three result cards stacked vertically.
Each result card contains:
Top section:

Rank badge (1, 2, 3) in a small circle on the top left
Category badge — colored label matching the category. Use distinct colors per category: Security = red, Integrations = blue, Implementation = green, Pricing = purple, SLAs = orange, References = teal
On the top right: the decision label badge — color coded green for Auto-Answer, amber for Review Required, red for Escalate to SME

Second section:

Label: "Matched Question"
The matched question text from the knowledge base in slightly muted text

Third section:

Label: "Answer"
The full answer text — this is the main content of the card

Fourth section — metadata row:

Confidence score displayed as: a thin horizontal progress bar showing the similarity score visually, with the percentage number next to it (e.g. "91% match"). Bar color matches decision color — green, amber, or red
Owner: show the owner field with a person icon
Last updated: show the date with a calendar icon
If is_stale is true: show a yellow warning badge that says "⚠ Answer may be outdated — review before use"

Bottom section:

A single button: "Mark as Used" — clicking this does not need to do anything functional in this prototype. It should show a brief "Noted ✓" confirmation. This button exists to signal that in a production system this action would log the usage and feed the learning loop.

Below all three cards (only shown after a search returns results):

A light grey information box with this text: "This prototype searches a knowledge base of 30 entries using semantic similarity. In a production system, the knowledge base would contain hundreds of verified entries with versioning, ownership workflows, and a feedback loop that improves match quality over time. Confidence scores reflect semantic similarity — not factual accuracy. Always verify answers marked Review Required or Escalate to SME before sending."
app.js behavior
On submit: send POST request to the backend /match endpoint with the question text. Handle loading state. Render results. Handle errors gracefully — if the backend is unreachable, show a clear error message in the results panel: "Could not connect to the matching service. Please ensure the backend is running."
Do not clear results when a new search begins — keep the previous results visible until new results arrive. This prevents jarring blank states.

Important Notes For Antigravity

The Gemini API key goes in the .env file and is loaded via python-dotenv. Never hardcode it.
The knowledge base embeddings are computed once at startup and cached in memory. Do not re-embed on every request — this would be slow and expensive.
Cosine similarity must be computed between the query embedding and each knowledge base entry's pre-computed embedding.
The staleness check compares review_due date against today's date at the time of the request.
The frontend makes requests to the backend. CORS must be enabled on the backend to allow this.
This is a prototype. No authentication, no database, no persistent storage. Keep it simple and functional.
